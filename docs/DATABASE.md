## ۲. چرا این معماری؟ (سازگار با میزبانی استاتیک)

- سایت فعلی روی **GitHub Pages استاتیک** بود (بدون بک‌اند). Supabase دقیقاً برای همین طراحی شده: کلاینت با **کلید عمومی (anon)** و مستقیم به دیتابیس وصل می‌شود و امنیت نه با پنهان‌کاری، بلکه با **RLS (امنیت سطح ردیف)** تضمین می‌شود.
- **به‌روزرسانی (دستور ۲۳):** میزبانی اصلی به **Vercel** منتقل شد (اجرای کامل Next.js + مسیرهای API)؛ کلید عمومی ساپابیس به‌عنوان متغیر محیطی پروژه (`NEXT_PUBLIC_*`) تنظیم شد و برای سیم‌کشی فاز D2 آماده است؛ امنیت همچنان بر عهدهٔ RLS است نه پنهان‌کردن کلید.
- منطق حساس (قیمت‌گذاری سفارش) در **تابع سمت دیتابیس** (`create_order`) اجرا می‌شود؛ کلاینت نمی‌تواند قیمت یا مبلغ را دستکاری کند.
- در آینده، برای دستیار AI و درگاه پرداخت واقعی، **Edge Functions** ساپابیس (بدون نیاز به سرور جدا) یا میزبان Node طبق مسیر «الف» دستور ۱۸ قابل افزودن است.

## ۳. استانداردهای امنیتی اعمال‌شده (راستی‌آزمایی‌شده ✅)

1. **RLS روی هر ۱۲ جدول** — پیش‌فرض: همه‌چیز رد می‌شود؛ فقط آنچه سیاست صریح دارد مجاز است (۲۷ سیاست فعال).
2. **هش‌گذاری رمز**: هیچ ستون رمزی در دیتابیس نداریم؛ احرازهویت با **Supabase Auth** است که رمز را با **bcrypt** هش می‌کند و ورود **کد یکبارمصرف پیامکی (OTP)** است — رمز خام هرگز ذخیره نمی‌شود.
3. **ضد دستکاری قیمت**: درج مستقیم در `orders` برای همه ممنوع است؛ ثبت سفارش فقط با تابع `create_order` که مجموع/ارسال/تخفیف را از جدول‌های خود دیتابیس محاسبه می‌کند (تست شد: ۲×۱۸۵۰۰۰ + ۸۰۰۰۰ ارسال − ۱۰٪ کوپن = **۴۱۳۰۰۰** دقیق).
4. **ضد ارتقای نقش**: ستون `role` در `profiles` با مجوز ستونی از نوشتن کاربران عادی خارج است (`revoke update / grant update(name, phone)`).
5. **حداقل دسترسی**: کوپن‌ها هیچ سیاست عمومی ندارند (فقط ادمین)؛ پیام‌های تماس فقط درجِ عمومی دارند و خواندن فقط ادمین؛ نظرات عمومی فقط «تأییدشده» می‌بیند.
6. **اعتبارسنجی ورودی**: چک‌کردهای دیتابیس (طول متن، بازهٔ قیمت، الگوی وضعیت/پرداخت/ارسال، سقف اقلام سبد ≤۵۰) + اعتبارسنجی داخل `create_order`.
7. **کلیدها**: `service_role` (کلید کامل) **فقط** در مکان امن محلی است — هرگز در کد، گیت یا کلاینت قرار نمی‌گیرد؛ کلید `anon` عمومی است و امنیتش را RLS تضمین می‌کند (تست شد: با anon، خواندن کوپن‌ها و پیام‌ها = خالی، درج در سفارش‌ها = خطای 42501).
8. **توکن‌های مدیر** (GitHub + Supabase): فقط در `/home/z/my-project/secrets/` (خارج از ریپو، سطح دسترسی ۶۰۰) و `.git/config` — طبق مصوبه ۵ و ۶ و دستور صریح مدیر؛ پیش از هر پوش، اسکن ضد نشت انجام می‌شود.
9. **TLS**: اتصال‌ها همگی HTTPS/WSS؛ اتصال مستقیم Postgres هم SSL الزامی است.
10. **ردپای زمان**: `created_at`/`updated_at` خودکار (تریگر `touch_updated_at`) برای ممیزی.

## ۵. مایگریشن‌ها (در مخزن — بدون هیچ راز)

```
supabase/migrations/
├── 0001_initial_schema.sql   ← جدول‌ها + نمایه‌ها + توابع + تریگرها + RLS + سیاست‌ها
└── 0002_initial_seed.sql     ← دادهٔ اولیه = کپی عینِ مقادیر فعلی کد (بدون دادهٔ جدید)
```

- اجرا: از طریق Management API (اسکریپت‌های `scripts/` محلی) یا SQL Editor ساپابیس.
- دادهٔ اولیه: فقط تنظیمات، دسته‌ها، محصولات، کوپن‌ها و بنرهای موجود در کد؛ **سفارش‌ها/مشتریان/نظرات/پیام‌های نمایشی عمداً وارد دیتابیس نشدند**.
- ساختار فعلی دو نسخه‌ای باقی می‌ماند تا تأیید سیم‌کشی: وب با دادهٔ نمایشی (مصوبه ۱۰) کار می‌کند؛ دیتابیس آمادهٔ اتصال است.

## ۷. فازبندی (قانون ۱۱)

- ✅ **D1 (همین دستور)**: پروژه + اسکیمای امن + RLS + توابع + دادهٔ اولیه + راستی‌آزمایی + مستندسازی — کد فریز.
- 🔲 **D2 — سیم‌کشی وب به دیتابیس** (فقط با تأیید مدیر): افزودن `@supabase/supabase-js`، اتصال محصولات/دسته‌ها/سبد→سفارش (`create_order`)، پیگیری سفارش واقعی، تماس با ما واقعی، ورود OTP واقعی (Supabase Auth) — نسخهٔ خروجی بعد از این فاز: **v1.1.0-web** (طبق قاعدهٔ شماره‌گذاری).
- 🔲 **D3 — پنل ادمین روی دیتابیس** (نقش `admin`): مدیریت محصولات/سفارش‌ها/نظرات/کوپن‌ها/بنرها/پیام‌ها/تنظیمات.
- 🔲 **D4 — دستیار AI با کاتالوگ زنده** (Edge Function یا میزبان Node — رفع محدودیت GitHub Pages).

**ورودی لازم از مدیر برای D2:** ۱) تأیید ترتیب سیم‌کشی (پیشنهاد: اول کاتالوگ+سفارش، بعد ورود OTP) ۲) سرویس پیامک برای کد یکبارمصرف (ساپابیس از کاواناس/ SMP ایرانی پشتیبانی می‌کند — انتخاب با مدیر) ۳) تأیید نگه‌داشتن میزبانی استاتیک فعلی در حین D2.
