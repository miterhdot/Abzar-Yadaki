## پیشنهاد ۱ — معماری «مونوریپو» (دریافت: ۱۴۰۵/۰۸/۱۱ — ثبت: دستور ۲۰)

**وضعیت:** 🟡 در انتظار تصمیم مدیر — هیچ تغییری در کد، ساختار یا پیکربندی انجام نشده است.

**منبع:** متن پیشنهادی معماری که مدیر از یک گفت‌وگوی مشاوره‌ای ارسال کرد (عینِ متن: «ضمیمه ۱» همین سند)، با جملهٔ آغازین: «پیشنهاد کوتاه: دو ریپوی جدا برای موبایل و وب نسازید. بک‌اند و API باید جدا و مشترک باشد، و بهترین شروع برای تیم کوچک یک مونوریپو است.»

### ۱. خلاصه وفادارانهٔ پیشنهاد دریافتی

| محور | پیشنهاد دریافتی |
|---|---|
| ریپو | **یک مونوریپو** به‌جای دو ریپوی جدا برای موبایل و وب |
| ساختار | `apps/mobile` + `apps/web` + `apps/admin` (پنل ادمین و سوپرادمین) + `services/api` (بک‌اند مونولیت ماژولار) + `packages/api-contract` (OpenAPI) + `packages/design-tokens` + `packages/shared-i18n` + `infra` |
| قرارداد API | OpenAPI-first: اول فایل OpenAPI، سپس تولید خودکار کلاینت وب و موبایل — جلوگیری از ناسازگاری |
| توکن‌های طراحی | رنگ/فونت/فاصله یک‌بار تعریف شود و هر دو کلاینت از آن بخوانند |
| CI | جدا برای هر بخش با فیلتر مسیر (`paths`) در GitHub Actions؛ مالکیت کد با `CODEOWNERS` |
| موبایل | برای شروع **چندسکویی** (React Native یا Flutter)؛ نیتیو (Swift/Kotlin) فقط جایی که لازم شد (دوربین/ویدیو/QR)؛ جدول مقایسه در متن اصلی |
| وب | رندر سمت سرور (مثلاً Next.js) برای دیده‌شدن در گوگل |
| ادمین | اپ جدا روی دامنه/زیردامنه جدا؛ برای سوپرادمین: احرازهویت دومرحله‌ای، محدودیت IP/VPN، لاگ کامل؛ اعمال نقش‌ها **در بک‌اند** |
| مقیاس | بک‌اند stateless پشت لودبالانسر؛ DB مدیریت‌شده + read replica؛ CDN برای رسانه؛ کارهای سنگین در صف؛ کش؛ صفحه‌بندی مکان‌نمایی؛ محدودیت نرخ؛ مشاهده‌پذیری؛ تست بار (بدون عدد فرضی) |
| گام‌های مقیاس | مونولیت ماژولار + یک DB + CDN + صف ← رید ریکا + موتور جستجو + کش قوی‌تر ← جداسازی ماژول‌های گلوگاه؛ شاردینگ فقط در صورت نیاز واقعی |
| هشدار | اشتباه رایج: میکروسرویس از روز اول — برای تیم کوچک توصیه نمی‌شود |
| پرداخت | نگهداشتن اطلاعات کارت توسط خودِ پروژه ممنوع؛ استفاده از صفحه پرداخت درگاه |
| روند تیم | `main` محافظت‌شده + PR؛ Trunk-based؛ سه محیط (توسعه/آزمایشی/تولید)؛ نشر موبایل با Fastlane/EAS + Feature Flag؛ اسرار فقط در GitHub Secrets |
| پرسش باز پیشنهاد | «تیم‌تان چه زبان‌هایی بلد است؟» + بازار هدف (روی انتخاب فروشگاه اپ، درگاه و ابر اثر می‌گذارد) |

| بک‌اند مشترک (`services/api`) | وجود ندارد؛ دو مسیر سرور (`/api`، `/api/ai-chat`) فقط در میزبانی Node اجرا می‌شوند؛ روی GitHub Pages استاتیک است و دستیار AI پیام جایگزین می‌گیرد (مصوب گزینه «ب» — دستور ۱۷) | ⬜ فاصله اصلی |
| اپ ادمین جدا | پنل ادمین داخل همان اپ است (`#admin` — گیت ورود + ۱۰ تب) | ⬜ متفاوت با پیشنهاد |

| CI مسیرمحور | فقط ورک‌فلو انتشار `deploy-pages.yml` وجود دارد (بدون تست/بیلد تفکیکی) | 🟡 نیمه‌همسو |
| سه محیط / Feature Flag / Secrets | ندارد (میزبانی فعلی: GitHub Pages استاتیک) | ⬜ فاصله |

### ۳. تحلیل — چه چیزی از پذیرش به دست می‌آید (بر اساس متن دریافتی + وضعیت فعلی)

1. **بستر بک‌اند واقعی:** همان سه محدودیت شناخته‌شدهٔ میزبانی استاتیک (دستور ۱۸ پیگیری ۴) برطرف می‌شود: درگاه پرداخت واقعی، دستیار AI زنده، سفارش‌گذاری سمت سرور.
2. **رشد موازی وب و موبایل بدون مخلوط‌شدن کد:** تفکیک پوشه‌ایِ صریح، قانون ۱ را از «تفکیک کد» به «تفکیک ساختار» هم ارتقا می‌دهد.
3. **قرارداد OpenAPI:** وب و موبایل هر دو از یک قرارداد تولید می‌شوند؛ ریسک ناسازگاری دو نسخه (نگرانی همیشگی قانون ۱) سیستماتیک حل می‌شود.
4. **مسیر مقیاس روشن:** طبق متن دریافتی، مونولیت ماژولار بعداً بدون بازنویسی به سرویس‌های مستقل تکه می‌شود.

### ۴. تحلیل — هزینه‌ها و ریسک‌های پذیرش در لحظهٔ فعلی

1. **جابه‌جایی گسترده مسیرها** (`src/` → `apps/web/src/` و ...) = تغییر ساختاری بزرگ → طبق بند ۹ و بند ۱۳-۷ قوانین نیازمند تایید صریح مدیر است و ممیزی کامل پس از اجرا می‌خواهد.
2. **توقف W5:** نسخه وب در آستانه خروجی `v1.0.0-web` است (پیش‌ممیزی چک‌لیست ۱ تا ۳ انجام شده)؛ بازآرایی ساختار درست قبل از خروجی، ممیزی را از ابتدا تکرار می‌کند — **توالی «اول خروجی، بعد بازآرایی» کم‌ریسک‌تر است.**
3. **فاز `services/api` به میزبان Node نیاز دارد:** تصمیم میزبانی هنوز باز است (سه گزینهٔ دستور ۱۸ پیگیری ۴: الف هاست ایرانی Node / ب هاست میزبان‌فا / ج ماندن روی Pages). بدون انتخاب میزبان، فاز API قابل اجرا نیست.
4. **نامعلوم بودن تیم/زبان:** انتخاب React Native یا Flutter (و زبان بک‌اند) مستقیماً به پاسخ پرسش باز پیشنهاد وابسته است — طبق قانون ۴، حدس زدن ممنوع است.
5. در متن دریافتی برای «یک میلیون ثبت‌نام» و میلیون‌ها کاربر اصول آمده ولی به‌درستی هیچ عدد فرضی‌ای داده نشده؛ برای پروژه فعلی این بخش «آماده‌سازی معماری» است نه نیاز امروز.

### ۵. طرح فازبندی پیش‌نویس (طبق بند ۱۱ قوانین — اجرای هر فاز فقط با تایید مدیر)

| فاز | محتوا | پیش‌نیاز |
|---|---|---|
| **M0** | تصمیم‌گیری مدیر (۴ پرسش بخش ۶) + به‌روزرسانی `docs/ROADMAP.md` و همین سند با تصمیم نهایی | — |
| **M1** | بازآرایی پوشه‌ای **بدون تغییر رفتار و گرافیک**: `apps/web` (کد فعلی) و `apps/mobile` (کد فعلی `src/mobile`)؛ اصلاح مسیرها در اسکریپت‌ها و ورک‌فلو؛ راستی‌آزمایی: lint + build + بازبینی بصری + انتشار Pages سالم | تایید M0 + اتمام/ثبت `v1.0.0-web` |
| **M2** | `packages/design-tokens`: استخراج متغیرهای رنگ/فونت مشترک دو کلاینت — با تعهد «صفر اثر گرافیکی» (پرت ۱:۱ فایل‌های طراحی حفظ می‌شود) | M1 |

هر فاز: بکاپ (کامیت) → اعلام «چه/کجا/چگونه» → اجرای فقط همان فاز با فریز بقیه → راستی‌آزمایی → ثبت در `COMMANDS.md`، `CHANGELOG.md` و در صورت رسیدن به خروجی، در `RELEASES.md`.

### ۶. پرسش‌های لازم از مدیر (بدون پاسخ، طبق قانون ۴ هیچ کاری انجام نمی‌شود)

1. **پذیرش/رد/تعویق** پیشنهاد مونوریپو؟ (گزینه کم‌ریسک: تعویق M1 تا پس از ثبت `v1.0.0-web`)
2. **تیم توسعه چه زبان/مهارتی دارد؟** (JS/TypeScript — Dart/Flutter — Swift/Kotlin — تیم نداریم؛ توسعه با هوش مصنوعی) ← پاسخ این پرسش انتخاب React Native/Flutter و زبان بک‌اند را تعیین می‌کند.
3. **اولویت زمانی:** اول خروجی `v1.0.0-web` یا اول بازآرایی ساختار (M1)؟
4. در صورت رسیدن به فاز M3: **کدام میزبان Node؟** (پیوند با تصمیم باز میزبانی — دستور ۱۸ پیگیری ۴)

پیشنهاد کوتاه: دو ریپوی جدا برای «موبایل» و «وب» نسازید. بک‌اند و API باید جدا و مشترک باشد، و بهترین شروع برای تیم کوچک یک مونوریپو است.

۱. ساختار گیت‌هاب

دو نسخه (موبایل و وب) در واقع دو کلاینت از یک بک‌اند هستند. «رابط فنی» بین آن‌ها همان API است، پس بک‌اند باید مستقل از هر دو باشد.

name github/                 (یک ریپو)
├─ apps/
│  ├─ mobile/             اپ موبایل
│  ├─ web/                سایت عمومی کاربران
│  └─ admin/              پنل ادمین و سوپرادمین
├─ services/
│  └─ api/                بک‌اند (مونولیت ماژولار)
├─ packages/
│  ├─ api-contract/       فایل OpenAPI (مرجع واحد API)
│  ├─ design-tokens/      رنگ، فونت، فاصله (از راهنمای سبک بصری)
│  └─ shared-i18n/        فایل‌های ترجمه
└─ infra/                 تنظیمات استقرار و محیط‌ها

- قرارداد API: اول فایل OpenAPI نوشته می‌شود و از روی آن کلاینت‌های وب و موبایل خودکار ساخته می‌شوند. این از ناسازگاری بین تیم‌ها جلوگیری می‌کند.
- توکن‌های طراحی: رنگ و فونت یک بار تعریف شود و هر دو کلاینت از آن بخوانند.
- CI جدا برای هر بخش: با فیلتر مسیر (paths) در GitHub Actions، تغییر در موبایل فقط تست و بیلد موبایل را اجرا می‌کند.
- مالکیت کد: با CODEOWNERS هر پوشه مسئول مشخص دارد.

چه موقع چند ریپو؟ اگر تیم‌های کاملاً جدا یا پیمانکارهای مختلف روی هر بخش کار می‌کنند و نمی‌خواهید به کد بقیه دسترسی داشته باشند. در این حالت هم ریپوی api-contract مشترک بماند.

۲. موبایل: نیتیو یا چندسکویی؟

| گزینه | مناسب برای | ضعف |
|---|---|---|
| چندسکویی (Flutter یا React Native) | شروع سریع، تیم کوچک، یک کد برای iOS و Android | کارهای خیلی سنگین دوربین و ویدیو ممکن است ماژول نیتیو بخواهد |
| نیتیو (Swift و Kotlin) | حداکثر کارایی و دسترسی کامل به سیستم | دو تیم و دو کدبیس، هزینه و زمان تقریباً دو برابر |

پیشنهاد: برای نسخهٔ اول چندسکویی. اگر تیم وب شما React می‌داند، React Native منطقی‌تر است و بخشی از دانش و کد (مثل منطق، تایپ‌ها) مشترک می‌ماند. اگر تیم تازه شروع می‌کند و UI زیبا و ثابت می‌خواهید، Flutter هم انتخاب خوبی است. فقط بخش‌های مثل ضبط و ویرایش ویدیو یا اسکن QR را اگر لازم شد، ماژول نیتیو بنویسید. بعداً اگر کاربر و درآمد بالا رفت، می‌توان بخش‌هایی را نیتیو کرد.

۳. وب و پنل‌ها

- وب عمومی: رندر سمت سرور (مثلاً Next.js) چون صفحهٔ کسب‌وکار و تجربه‌ها باید در گوگل دیده شوند.
- پنل ادمین و سوپرادمین: یک اپ جدا در همان مونوریپو و روی دامنه یا زیردامنهٔ جدا. دلیل: امنیت بالاتر. برای سوپرادمین احراز هویت دومرحله‌ای، محدودیت IP یا VPN و لاگ کامل اقدام‌ها.
- دسترسی‌ها (ادمین، سوپرادمین) را در بک‌اند با نقش‌ها اعمال کنید، نه فقط با مخفی کردن دکمه در رابط.

۴. چطور برای میلیون‌ها کاربر آماده شویم؟

یک نکته: «یک میلیون ثبت‌نام» با «یک میلیون کاربر همزمان» خیلی فرق دارد. معمولاً همزمانی چند درصد از کل است. ولی باید از اول درست بسازید که رشد، بازنویسی نخواهد.

اصول از روز اول
- بک‌اند بدون حالت (stateless) پشت لودبالانسر، تا با اضافه کردن سرور مقیاس بگیرید.
- پایگاه داده مدیریت‌شده با پشتیبان‌گیری، و بعداً کپی‌های فقط‌خواندنی (read replica) برای جستجو و گزارش.
- CDN برای عکس و ویدیو. فایل‌ها هرگز از سرور اصلی عبور نکنند؛ آپلود مستقیم با لینک امضاشده.
- کارهای سنگین ناهمزمان: تبدیل ویدیو، بررسی هوش مصنوعی، اعلان‌ها، ارسال ایمیل در صف پردازش شوند، نه در پاسخ مستقیم API.
- کش برای صفحات پرتکرار (صفحهٔ کسب‌وکار، دسته‌بندی‌ها).
- صفحه‌بندی با مکان‌نما و ایندکس درست پایگاه داده. جدول‌های بزرگ (تجربه‌ها، اعلان‌ها، دفتر کل) را از قبل برای افزایش حجم طراحی کنید.
- محدودیت نرخ و حفاظت در برابر سوءاستفاده.
- مشاهده‌پذیری: لاگ ساخت‌یافته، متریک و هشدار.
- تست بار قبل از رسیدن به اوج: اول هدف‌های واقعی (تعداد درخواست در ثانیه، زمان پاسخ) را با داده‌های واقعی خودتان تعیین کنید، بعد تست کنید. من عدد فرضی نمی‌دهم چون به رفتار کاربران شما بستگی دارد.

مرحله‌به‌مرحله
1. شروع: مونولیت ماژولار + یک پایگاه داده + CDN + صف.
2. رشد: کپی‌های خواندنی، موتور جستجوی جدا، کش قوی‌تر.
3. اوج: جدا کردن ماژول‌هایی که گلوگاه شدند (پردازش ویدیو، هوش مصنوعی، پرداخت) به سرویس مستقل. شاردینگ فقط اگر واقعاً لازم شد.

اشتباه رایج: از اول میکروسرویس بسازید. برای تیم کوچک، هزینهٔ نگهداری و هماهنگی بیش از فایده است. مونولیت ماژولار با مرزهای روشن بین ماژول‌ها بعداً به‌راحتی تکه‌تکه می‌شود.

پرداخت: برای کاهش خطر و بار امنیتی، اطلاعات کارت را خودتان نگه ندارید؛ از صفحهٔ پرداخت خود درگاه استفاده کنید.

۵. روند کار تیم در گیت‌هاب

- شاخهٔ main محافظت‌شده، تغییرات فقط با Pull Request و بازبینی.
- شاخه‌های کوتاه‌عمر و ادغام مکرر (Trunk-based) به‌جای شاخه‌های بلند.
- سه محیط: توسعه، آزمایشی (staging) و تولید، با استقرار خودکار.
- نشرهای موبایل با ابزار خودکار (Fastlane یا EAS)، همراه با Feature Flag تا بشود قابلیت‌ها را بدون انتشار نسخهٔ جدید خاموش و روشن کرد.
- اسرار و کلیدها فقط در GitHub Secrets، با Dependabot و بررسی امنیتی کد.
